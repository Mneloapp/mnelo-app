# Delivery architecture review — September 12, 2026

Status: **owner-authorized migration, implementation in progress; not deployed**. After this review, the owner explicitly instructed implementation of the established WhatsApp-style communication model using an existing protocol, and reaffirmed simplicity, privacy and no AI. This authorizes temporary end-to-end encrypted delivery storage in place of the earlier no-ciphertext-at-all rule. It does not authorize server-readable content or permanent chat archives. Current builds still use the former direct-only transport until a verified migration is installed. No WhatsApp branding, proprietary code, feeds or additional product features are introduced.

## Finding

Optimizing the present transport cannot make content available when its only reachable copy is on a suspended/offline sender. A local outbox is useful but cannot substitute for an independently reachable delivery service. Push can notify or request execution; it does not contain the missing message or guarantee both participants run simultaneously.

The recommendation is **asynchronous end-to-end encrypted delivery with temporary server storage**, retaining local history and participant-controlled backups. Keep WebRTC for real-time call media; remove the message data channel as a prerequisite for call control. This is a protocol migration, not a UI patch or an instruction to upload existing plaintext packets.

## Options

| Choice                                        | Privacy/storage                                                                                                     | Result                                                                                                                                              |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repair the present direct-only design         | No durable server content, including ciphertext                                                                     | Can improve foreground latency, call control and status clarity. Cannot deliver after the sender disappears before the recipient becomes reachable. |
| **Temporary encrypted mailbox — recommended** | Only opaque end-to-end encrypted envelopes/media retained until acknowledged or expiry; no server-held content keys | Sender can disconnect after server acceptance. Recipient fetches later without the sender. Fits ordinary messenger use.                             |

Increasing VPS size, keeping every peer connection alive, putting content in RAM only, or adding more push retries does not remove the availability trade-off. RAM-only storage loses accepted deliveries on process/host restart and is still server processing/storage. A conventional cloud chat-history database is unnecessary for the proposed product.

## Proposed privacy contract and retention

Recommended initial undelivered-content limit: **30 days**, configurable and disclosed. This follows the published WhatsApp undelivered-message limit; it is an upper bound, not a claim that current Mnelo already implements it. A message beyond the limit becomes expired/undelivered, not delivered. Retries must not silently reset an expired message's retention deadline.

- Conversation content is encrypted on the sending device before any server upload. Decryption/session private keys remain on participants' devices. TLS to the server or SQLCipher at rest alone is insufficient.
- An authenticated recipient commits a verified/decrypted message and the required ratchet state durably before issuing delivery acknowledgement. The service removes that recipient's envelope on acknowledgement. A server upload acknowledgement never produces the delivered leaf.
- For groups, delivery and expiry are tracked per authorized recipient/device. Membership revisions and removal must bind cryptographically to the authorized send set; stale senders cannot merely trust an unverified server roster. No entire-group plaintext or shared unversioned key shortcut.
- Photos, files and voice notes are encrypted with library-supported attachment encryption, uploaded as opaque objects, and referenced/authorized through encrypted messages. Remove the object after all addressed recipients finish durable download or expiry. Message-envelope receipt alone must not prematurely delete an attachment.
- Queue data must be excluded from long-lived backups, request logs, analytics, crash dumps and CDN caches. Replica/object deletion and crash-recovery storage must follow a documented, tested lifecycle. Do not claim forensic instantaneous erasure from every SSD/WAL/snapshot; no undeclared durable copies may defeat the retention promise.
- Server-visible metadata remains: authenticated account/device identifiers, public keys/prekeys, queue routing, opaque IDs, size, creation/expiry, quota counters and push routes. Minimize it and disclose it. No claim of zero metadata or anonymity.
- Histories remain in participant vaults. Deleting one's local history does not delete another participant's copies. Account deletion cancels relevant queued deliveries according to explicit recipient/sender policy; it does not remotely wipe already delivered content.
- Backups remain user-chosen and locally encrypted. The mailbox is not history sync, account recovery or backup escrow. No AI conversation processing is introduced.

Potential future public wording, usable only after implementation and review: “Your conversations stay between their participants. Mnelo cannot read them. Encrypted messages wait temporarily for delivery and are removed after delivery or expiry. Each person controls their own history and backups.” This explicitly replaces “Mnelo never stores even encrypted information.” It is not an absolute promise against compromised endpoints, malicious client updates or all metadata access.

## Protocol and client boundaries

1. Use an established asynchronous E2EE protocol implementation, with authenticated identity keys, published signed/one-time public prekeys, ratcheted sessions, replay protection and bounded out-of-order handling. Never build a new cryptographic protocol from AES + a static peer key. Review identity changes, key verification/transparency, prekey exhaustion/replenishment, concurrent session writes and restored-device rollback.
2. Spike the maintained native implementation on both existing Expo development builds before selecting the package. The official `signalapp/libsignal` repository exposes Rust-backed Swift/Java interfaces but explicitly says use outside Signal is unsupported and APIs can change. Its AGPL-3.0 license and distribution obligations require evaluation before adoption. It is **not** an assumed drop-in supported React Native dependency; no dependency has been selected by this document.
3. Preserve SQLCipher, local IDs/history, profiles, UI, notifications, registration and local backups. Introduce separate `MessageDelivery`, `SessionCrypto` and `CallSignaling` boundaries instead of sending `packetSchema` JSON through a plaintext server endpoint. A new transport alone is not E2EE.
4. Persist the outbound encrypted envelope, session-state advancement and stable idempotency ID atomically, before network submission. Persist verified inbound content/session advancement/deduplication atomically before acknowledging. A crash must neither reuse a message key nor lose an accepted message.
5. Use an authenticated HTTPS API for durable upload/fetch/ack and WebSocket for immediate events while active. A WSS disconnect cannot lose server-accepted content. No perpetual background socket or peer scanning is required for messages.
6. States are explicit: local pending → server accepted → recipient committed → read. Leaf remains absent before recipient delivery, outline when delivered, filled when read. Offline/failed/expired states are understandable on inspection. Receipts and reactions use the same acknowledged encrypted envelope mechanism, with idempotent application.
7. Unknown contacts arrive in a bounded inbox with reply/accept/block controls. Recipient need not search/add the sender first. Locally saved address-book name wins. Rate limiting, sender enrollment, first-contact quotas, server-enforced revocable authorization and abuse controls must be designed before enabling arbitrary wakeups/queues. No name/number is a proof of cryptographic identity.
8. Recipient startup/foreground/reconnect drains bounded queue pages; retry uses backoff and deduplication. iOS push is a wake/alert hint. If a notification-service extension is added for local sender-name resolution/decryption, its key/database access, atomic concurrency and fallback must be reviewed and physically tested. PushKit is reserved for live calls. OS permission denial, force-stop and no connectivity remain explicit limits.

## Calls

Use the existing native CallKit / Android Telecom integrations and WebRTC media stack, subject to real-device validation. Call initiation/accept/decline/cancel must travel over an independently authenticated signaling path, with monotonic state transitions, stable call IDs and stale-event rejection. A pending photo or unopened chat must never prevent answering a call.

Live call invitations expire within a short ringing window (proposed 45 seconds). Store only bounded signaling state and, under the new exception, an encrypted missed-call event for later delivery. Never replay an expired invitation as a fresh incoming call after reconnect. No audio/video recording or storage is required.

Retain authenticated DTLS-SRTP media with identity-bound signaling. Current deployment uses relay-only coturn. Add and validate TURN-over-TLS/443 for restrictive networks if deployment/network evidence supports it; it needs correct TLS termination/port separation from the existing web endpoint. Do not promise that changing the queue fixes media negotiation or native audio. Do not switch to an SFU whose transport terminates media encryption without an explicit E2EE design.

## Migration and acceptance

1. Preserve the build 10 fixes and current vaults. Finish its reproducible checks and record remaining physical failures honestly.
2. Owner adoption of the temporary-ciphertext exception is complete. Before enabling persistent content on the live server, complete the two-platform crypto integration feasibility and license review.
3. Implement a versioned server mailbox and isolated synthetic-device tests first. Use the existing small development server where measurements permit; no new paid account is a prerequisite for the design. Storage, egress and reliability capacity must be measured before increasing enrollment. This document makes no unmeasured cost/capacity promise.
4. Add native session storage, encrypted message/media delivery and separate call signaling. Enroll device keys explicitly, no silent replacement. Do not upload historical chats. Old clients must get an honest update-required/unsupported state for new delivery, never an insecure downgrade. Select one transport per recipient/message to avoid duplicate history.
5. Complete blocked sender, forged key/receipt, replay, expired queue/object, recipient isolation, group removal, quota, tampered attachment, secret-scan and crash-recovery tests. Verify queue deletion across the actual storage lifecycle. Public independent protocol/deployment review remains required.
6. On two iPhones: B offline → A sends → server accepts → A goes offline → B reconnects → B gets text/photo/voice note; repeat with server restart, ack loss, expired content, app suspension, multiple messages and pending media during calls. No server acceptance without durable storage; no delivered leaf before recipient commit. Repeat on Android.
7. Verify simultaneous call actions, locked/cold start, denied permission, Wi-Fi/cellular switching, restricted UDP networks, expired ringing and later missed-call event without phantom rings. Measure time to server acceptance, recipient delivery and first bidirectional audio separately. No claim of WhatsApp-equivalent reliability from unit tests or a single successful call.

## Primary sources checked September 12

- [WhatsApp privacy policy](https://www.whatsapp.com/legal/privacy-policy): undelivered messages remain encrypted for up to 30 days; delivered messages are not ordinarily retained, and there is a separate temporary media-forwarding case. This demonstrates a different storage model from present Mnelo, not permission to copy all WhatsApp practices.
- [WhatsApp privacy explanation](https://www.whatsapp.com/privacyquestions): Signal Protocol protects personal message content before it leaves the device.
- [Signal PQXDH](https://signal.org/docs/specifications/pqxdh/), [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/), [Sesame](https://signal.org/docs/specifications/sesame/): asynchronous key establishment and session management. Specifications are not substitutes for a vetted implementation/integration.
- [Official libsignal](https://github.com/signalapp/libsignal): native wrappers, external-support limitation and license.
- [Apple background updates](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app): low-priority background execution is not guaranteed.
- [Apple APNs requests](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns): provider expiry/delivery semantics.
