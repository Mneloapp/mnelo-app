# Build 31: background delivery receipts and faster call setup

A recipient could receive a notification while Mnelo was closed, but the sender's delivery leaf appeared only after the recipient opened the app. The notification extension now queues and attempts an encrypted delivery receipt after the authenticated message has been saved in the encrypted inbox and validated against the contact, phone, chat membership, deletion and block state. It does not project the conversation or mark it read. The leaf therefore becomes a gray outline on confirmed receipt; green still requires the existing read receipt.

The inbox stores the receipt ID atomically with the outbox insertion. Duplicate notification execution and subsequent app projection reuse that record; failed uploads keep their sealed ciphertext for the ordinary pump to retry. Notification HTTP requests have a shorter bounded timeout so a failed receipt attempt does not unnecessarily delay the preview. Only the exact receipt is sent. No unrelated outgoing content, new identity, key publication or server deletion is performed by the extension. Attachment descriptors are durable in the inbox; downloading/acknowledging encrypted media remains the app's normal path. iOS still controls notification extension execution and first-unlock access.

Call setup previously waited for all ICE gathering on both peers before exchanging offer/answer, including slow fallback TURN transports. Calls now send the signed description after the first relay candidate has had a 200 ms settling interval, or when gathering completes. The remaining candidates follow in an authenticated description update; matching ICE credentials, media sections and DTLS fingerprints are required before candidates are added without renegotiation. The initial offer/answer remains usable by older builds. Relay-only routing and the existing signed/encrypted signaling transport remain intact. The implementation follows the early candidate exchange approach described by [WebRTC](https://webrtc.org/getting-started/peer-connections).

Call control and media signaling have priority over ordinary receipts/messages and are flushed before maintenance and between inbox/acknowledgement items. They retain durable retries and the same paced request budget. This removes backlog-dependent waits without treating an unconnected call as active. The call timer still begins only after the media connection succeeds.

On iOS, an outgoing ringing call now plays a quiet generated 425 Hz telephone ringback through the CallKit-activated audio route, with one second on and four seconds off. It stops on acceptance, connection, hangup, rejection, timeout, audio deactivation and provider reset. Incoming calls keep the system ringtone. The implementation uses [CallKit audio activation](<https://developer.apple.com/documentation/callkit/cxproviderdelegate/provider(_:didactivate:)>) and does not activate an independent audio session.

Tapping a Calls history row opens the call screen immediately for that record's voice/video type. Its information button separately opens call actions. An existing call is resumed instead of starting another one. History/search call actions also pass only the accepted name/key fields when resolving the saved contact, fixing the validation error shown in the screenshot. Group call participant selection remains available before inviting a group.

## Validation

Full checks passed 641 tests: 483 Jest tests across 92 suites, 3 server tests and 155 device/protocol tests, plus TypeScript, lint, formatting, security, environment, localization and brand checks. Actual Signal encryption and authenticated loopback HTTP with separate shared-vault connections prove delivery before recipient app opening, unread state, duplicate handling, failed receipt upload/recovery and later read status. A two-peer signaling fixture proves offer/answer completes while gathering is still pending and adds fallback candidates without resetting the remote descriptions. Component/native-bridge tests cover history actions and ringback lifecycle.

The native archive, immutable public source CI and TestFlight distribution are recorded in BUILD_LOG when completed. The final iOS ringback routing, notification extension execution and two-phone latency require acceptance on the newly installed build; automated fixture results are not a claim of physical-device acceptance.
