# Build 30: delivery recovery, notifications, calls and media

The previous Photos picker selected one item and exported videos at their original size. A camera video exceeding the existing 10 MB attachment limit therefore failed before a message could be saved, while the generic action handler hid the size error. Its default iCloud policy could also fail to retrieve originals that were not on the phone. The screenshot alone does not identify which of those failures occurred on the owner's device.

Photos now permits an ordered selection of up to ten photos/videos; Camera remains single capture. On iOS the existing Expo ImagePicker exports videos with its MediumQuality preset to a compatible, smaller MP4, and permits downloading iCloud sources. Still images keep the existing 1600-pixel JPEG preparation. Photo decoding is sequential and native image handles are released after each conversion. Failed preparation cleans up the prepared cache copies and does not send part of that selection. These options are supported by the installed SDK 57 ImagePicker implementation and [official ImagePicker documentation](https://docs.expo.dev/versions/latest/sdk/imagepicker/).

The send helper checks every selected file before committing the first message, then saves items in selection order, reading only one base64 file at a time. Multiple items enter the durable outbox before an explicit flush. Each photo/video is an individual existing message kind, so this does not change the protocol or introduce an incompatible album format. A partial database failure reports the number saved, does not retry those items, and cleans up unsent cached copies. Voice previews remain available if their commit fails. Video size, duration, picker/download and file-read failures now have specific EN/KA copy; unknown errors retain the safe generic message.

The existing per-file limit is still 10 MB and video duration metadata is bounded at one hour. Compression reduces resolution and cannot guarantee every long video fits. An oversized prepared video now asks the user to trim it or select a shorter clip. Files selection keeps original file content; the automatic video export applies to Photos/Camera. No library-wide permission, server thumbnail service, new dependency or transport size increase was introduced.

The media checkpoint passed 614 tests (466 UI/unit, 3 server and 145 device/protocol), TypeScript, lint, formatting and the security/environment/localization/brand gates. Regression checks cover ordered mixed selection, cancellation, camera options, bad duration metadata, conversion/resource cleanup, preflight rejection without partial sending, valid video packets, partial local commits, voice retry and user-visible error mapping. A native macOS AVFoundation probe using the same export preset converted a synthetic six-second 1080x1920 ProRes source from 32,800,953 to 628,341 bytes (320x568 MP4), preserved six-second duration and decoded its poster. This verifies the native codec operation, not physical iPhone Photos/iCloud behavior. The actual prepared MP4 and two JPEGs then traversed the production Signal/encrypted-attachment pipeline over loopback between fictional accounts; the recipient retained exactly three matching files, including after retry. Evidence is private under artifacts/media30-fixture.

Signed build verification and TestFlight availability are recorded in BUILD_LOG. ## Delayed delivery and receipts

The owner's connected iPhone had 111 pending Signal events and no pinned peer identity. The old pump retried the same unready peer for every queued event, exhausted identity lookup limits, and subsequently hit delivery limits while draining. Once the lookup window reset, the unchanged native Signal implementation successfully decrypted, projected and acknowledged incoming messages; the owner confirmed two-way delivery and calls. No account, key, history or identity pin was reset. A later diagnostic snapshot showed 191 uploaded events and 125 projected/acknowledged inbox events, with no unsent events in that snapshot. The owner then confirmed that receipt leaves appeared.

A durable peer-level lookup backoff now bounds those retries across restart. Signed hosted commands share an 80-per-minute queue, with a one-minute pause after rate limiting. Recent messages and protocol receipts/call controls precede old deferred work; deferred records remain durable. Explicit sends flush their own message ID instead of waiting behind the first 50 historical deliveries. Identical push registrations are idempotent on the existing backend, while route changes retain their rate limit and ownership checks. Server limits and identity verification are unchanged.

The leaf means recipient receipt: an empty gray contour after delivery, solid green after the recipient marks the conversation read. Uploading or queuing alone does not create a leaf. Group status still waits for the corresponding member receipts. Tests verify these transitions and do not simulate a delivered state merely to change the icon.

## Notification and call presentation

A native notification service extension decrypts the targeted message on the recipient's phone using the existing encrypted shared vault and Signal implementation. It can commit the durable cryptographic inbox but cannot acknowledge, project, mark read, send a reply, create an identity or publish new keys. The app resumes that inbox normally. Names use the same local phonebook/profile resolution; text is bounded, and media uses an appropriate label. Unknown, blocked, deleted, mismatched-phone, unrelated-group and unavailable messages retain the generic alert. APNs continues to receive an opaque event ID, not message text or the contact name. The containing app resolves notification taps from its local vault and respects the user's iOS preview settings.

The extension has a 20-second fallback deadline. First-unlock/keychain availability, network and iOS extension execution can still prevent a preview. The [`UNNotificationServiceExtension` delivery contract](https://developer.apple.com/documentation/usernotifications/modifying-content-in-newly-delivered-notifications) is used with `mutable-content: 1` for message alerts only. There is no extension network bypass or plaintext file cache. The new target is `com.mnelo.messenger.notifications`; main, sharing and broadcast identifiers stay unchanged.

CallKit reports the initial push immediately, then updates its caller name/phone only after the authenticated call invite resolves locally. Native Mnelo branding remains distinct from the caller, and the in-app heading also labels the call as Mnelo voice/video. Call duration starts at the first media connection, survives route changes and reconnect updates, and stops at call end. [CallKit's system screen](https://developer.apple.com/documentation/callkit/cxcallupdate) owns its controls; custom quick replies are provided in Mnelo's incoming-call screen and can be edited from Settings. Selecting a reply saves a private direct message before declining; opening or editing the menu sends nothing. Three local replies are stored in the encrypted vault and cleared with account erasure.

## Quotes and layout

Tapping a quote checks that the original belongs to the same conversation, loads earlier pages as needed, centers the message and highlights it briefly. An unavailable/deleted local original produces a notice; changing chats or manually scrolling cancels a pending jump. Sending a new message retains the existing jump-to-latest behavior.

Text bubbles no longer wrap the timestamp as a second flex line whose changing height could be clipped on iOS. Text can wrap vertically while the timestamp keeps its own space; media keeps its separate/overlaid metadata. The swipe-to-reply wrapper no longer clips a message vertically, and the variable-height inverted list keeps native subview clipping disabled. Browser inspection of real components at effective widths 271 and 390 CSS pixels showed complete Georgian text, contour/green receipts, editable replies and a running call timer with no console errors. This is not a physical-device layout claim.
