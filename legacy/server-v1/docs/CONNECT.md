# Connect requests

Connect retains the minimalist text → interpretation → relevant people flow. The current interpreter is `rules-v1`, a pure server-side `IntentInterpreter` with no network calls or paid model dependency. An optional provider can later be selected inside the Edge Function only, with schema validation, a deadline and deterministic fallback. Mobile receives bounded structured data and never provider secrets.

The initial vocabulary covers service, professional, social activity, person/capability, opportunity and product-related connections. Examples include electrical installation, plumbing, accounting, design, tennis, volunteering, photography and bicycles. Supported English and Georgian keywords are explicit in `_shared/intent.ts`. This is a limited deterministic vocabulary, not general language understanding. Unknown or ambiguous capabilities require the user to clarify. Local activities/services ask for an area only when missing; remote activities do not get an invented location. No confidence percentage is produced.

Every request preserves the exact raw text. Clarification answers are stored separately as `confirmed_capability` and `confirmed_area`, alongside the normalized capability, intent type, approximate area, detail text, date, timezone and interpreter version. Known Georgian localities map to coarse place names; explicit area answers reject digits/coordinates and street/address-shaped text. Raw requests remain owner-only. Matching must use the permitted derived fields, not expose the original text or infer private GPS.

Relative today/tomorrow dates resolve using the supplied, validated IANA timezone at server interpretation/publication time. Unspecified times stay absent; invalid calendar dates are not invented. The confirmation shows an explicit date. A draft spanning midnight should be reinterpreted before publication; the final stored date is the publication interpretation. Availability and language refinements remain separate matching signals.

`connect-intent` verifies Auth, consumes a caller-scoped attempt before parsing, applies a strict input schema and re-runs interpretation when publishing. Unknown fields such as an actor/role are rejected. The service-only publication RPC gets its actor from the verified server session. Clients cannot insert requests or invoke that privileged procedure directly. User-confirmed terms are self-described intent, not verified professional qualifications.

Publication atomically creates the matching request and exactly one normalized Need/Offer row. A client UUID plus canonical input SHA-256 fingerprint makes retries idempotent and rejects reuse with different content. The fingerprint is a consistency check, not a credential. There are at most 20 active requests per user; interpretation/publication is limited to 40 attempts/hour and state changes to 60/hour. Local tests exercise real Auth, not a mocked database.

Own requests use 30-row timestamp/UUID cursor pages. They can be active, paused or closed (database `completed`). Pause/close expires candidate access; reactivation requires a fresh matching run. Request screens fetch a specific owned need by ID instead of scanning a first page. Publishing invalidates the needs cache. The matching engine and public-safe active intent summaries are now connected; see [MATCHING.md](MATCHING.md) for evidence, privacy and ranking behavior.
