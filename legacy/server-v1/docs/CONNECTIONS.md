# Mnelo contextual connections

Unknown people cannot open a direct conversation. A current privacy-authorized request must be accepted by its recipient. Existing connections reopen the unique conversation through an authenticated lookup; the app never relies on searching only a loaded page of chats.

`connection_state` returns the relationship, pending direction, eligibility and the exact structured context to review. For a Connect result, the server requires a live candidate for that request and recipient, and checks the submitted context against its canonical capability/coarse area/date/detail summary. The original raw request remains private. Detail identical to the raw text is omitted. Only the displayed reason and optional message are shared. Manual requests require an explicit reason and the same privacy/block rules.

`send_connection_request` derives the sender from Auth, takes a persistent client UUID, serializes the pair and verifies exact payload equality on retries. Reusing a key with a changed payload conflicts. A pending opposite-direction request requires explicit review; it never silently accepts. Limits are 20 new requests/hour and a 24-hour cooldown after decline. Pending requests expire after the database's 14-day default; list/send/response procedures enforce expiry without depending on a client timer. Expired requests cannot be accepted.

`respond_connection_request` authorizes accept/decline only for the recipient and cancel only for the sender. Acceptance atomically stores the connection, direct conversation and both memberships. It preserves the reviewed context and server-derived service/business/social purpose. An optional invitation message becomes the first message exactly once. Accept, decline and cancel retries are idempotent; accepting again returns the same conversation. Blocks override even a retry.

Requests use 30-row `(created_at,id)` cursor pages, a virtualized list and private participant RLS. Connections use bounded 50-result name/username search. The inbox receives only authorized INSERT/UPDATE events. A channel join is not treated as PostgreSQL readiness: the app refreshes at join and again at the `postgres_changes` system-ready event, closing the registration gap found in real integration testing. See [Supabase's protocol](https://supabase.com/docs/guides/realtime/protocol) and [Postgres Changes authorization](https://supabase.com/docs/guides/realtime/postgres-changes).

Local verification: four actual Auth users cover matching-context integrity, ownership/role denials, idempotency, atomic acceptance, invitation preservation, incoming/accepted Realtime events, decline/cancel/expiry, tied cursor pages and blocks. Privileged historical timestamp fixtures are local-only; assertions use user tokens. A two-browser local OTP flow additionally exercised actual matching, sending, recipient acceptance, reply and reopening the resulting conversation. No physical-device PASS is implied.

Limits: requests are not an unrestricted messaging route. Relevant-only defaults can hide an arbitrary username until a real matching result or authorized relationship exists. Historical requests may show a generic profile label if current profile access is unavailable. Cloud push delivery follows Phase 14. Final abuse, concurrency, retention and offline acceptance remain later checkpoints.
