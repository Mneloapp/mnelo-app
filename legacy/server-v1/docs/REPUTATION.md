# Mnelo trust and reputation

Reviews describe a completed service or business connection. They are not a social score, transaction verification, proof of payment, or evidence that Mnelo independently inspected the work. Ordinary social connections have no completion/rating requirement. In this V1 foundation each connected pair can complete and review its original connection once; repeat transaction records are not implemented.

Both participants explicitly confirm completion through `confirm_connection_completion`. Auth determines the actor; a pair lock and connection row lock serialize concurrent confirmations. A first confirmation leaves the connection incomplete. Only two actual participant confirmations set completed_at. No client can insert confirmations for somebody else, alter connection purpose or mark the connection complete directly. The purpose was derived from the accepted matching request. A manual social request cannot be reclassified by the client merely to obtain a rating.

`submit_connection_review` derives the subject as the other participant and requires service/business purpose, both confirmations and no block. Each author gets one immutable 1–5 rating and optional 1,000-character comment. Exact retry returns the same review; changed content conflicts. No client-chosen subject/author or direct table write is accepted. Completion is bounded to 20/hour and reviews to 5/day. These limits remain subject to the final abuse review; SQL failures roll back the transaction.

Before publishing, the UI explains the audience, optional nature and lack of editing, and asks the author not to include private information. Profile-visible projections expose only review ID, rating, comment, date, broad purpose and whether it belongs to the viewer. Raw author IDs and private connection IDs/context are not readable through the reviews table. Comments are user-authored public-to-profile-viewers content, not a promise of anonymity: an author can identify themselves in their text.

A private `published_reviews` view includes only published reviews for mutually completed eligible connections. Profile averages/counts, ranking signals and result evidence all use this same view. Server-only status can hide an abusive review; hiding expires matching evidence and removes the review from aggregates. Blocking does not erase an already published review from other authorized viewers. An author/subject block prevents new review actions and their mutual profile access. Account deletion retention/removal follows Phase 17; no finalized legal retention policy is claimed.

`verification_status` remains server-written only. `profile_verifications` returns the actual current scope: identity, professional or business. Future-dated and expired records are excluded. UI copy names the verified scope; no badge is invented from a profile claim or an ordinary review. No real verification provider, issuer workflow or credential check has been configured. A future service-side issuer must retain auditable evidence privately; do not insert verification records based on an unverified client assertion.

Navigation: conversation overflow → Connection → explicit completion → optional review. Me → Connections → Completed connections provides a private 30-row cursor history. Public-safe profile reviews use 20-row cursor pages. The private inbox receives connection/completion INSERT/UPDATE events, so the peer's confirmation updates the open screen.

Actual local checks: three-user integration tests uncompleted/unilateral/social/outsider denials, spoofed writes, concurrent confirmation, retry/immutability, raw identifier protection, review aggregation/moderation and current verification scopes. Temporary verification fixtures are removed by the test. Matching and connection regressions plus 52 pgTAP checks pass. Two separate local OTP browser accounts completed a real accepted development connection and published/viewed one explicitly labeled development review; no native/device claim.
